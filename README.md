# lab-sre-data-structures

Лаба к статье «Почему SRE надо знать всякое: прод стоит на структурах данных». Когда знакомые инструменты начинают тормозить, полезно проверить, какая работа скрывается за одним запросом. Здесь можно увидеть очередь nginx, сравнить B-tree с полным перебором и заставить регулярку тратить вчетверо больше времени на вдвое более длинную строку.

Все замеры запускает один скрипт на Python без сторонних библиотек. Сырые результаты лежат в `results/`: версия Python, ОС, дата прогона, отдельные повторы и digest образа для Docker-режимов. Время на твоём компьютере будет другим; важны форма роста и план выполнения.

## Быстрый старт

Нужны Python 3.11+, git, make; для контейнерных примеров — работающий Docker. Сохранённый прогон сделан на Python 3.15.2 и Docker Desktop на macOS arm64. Образы: `nginx:1.31`, `postgres:18.6`, `redis:8.10`. Теги могут обновляться; точные скачанные образы записаны как RepoDigests в JSON.

```bash
make local       # регулярка, хеширование, git bisect
make docker      # nginx, Postgres, Redis, наблюдение conntrack
make all         # всё
```

Каждая цель перезаписывает свой `results/<режим>.json`. Можно запустить отдельно `make regex`, `make hashing`, `make bisect`, `make nginx`, `make postgres`, `make redis` или `make kernel`.

Контейнеры временные, без томов с данными: скрипт удаляет только созданные им контейнеры в `finally`. Postgres и Redis запускаются без сети; nginx публикует случайный порт на `127.0.0.1`. Конфиг nginx монтируется из временного каталога только для чтения. Для скачивания образов нужен доступ к registry. Посторонние контейнеры и настройки Docker не меняются. Postgres создаёт 5 млн строк, Redis — миллион уникальных значений; на это нужны память и свободный диск Docker VM.

## Что измеряем

| Режим | Метод | Что смотреть |
| --- | --- | --- |
| `regex` | `re.search` на строке `x` + N пробелов + `x`, три повтора | Медиана времени растёт примерно вчетверо при удвоении N. `rstrip()` сразу видит, что последний символ не пробельный |
| `hashing` | 200 000 ключей MD5, кольцо со 160 виртуальными точками на узел | Доля переехавших ключей при 4 → 5 и 10 → 11; виртуальные точки дают разброс относительно математического ожидания |
| `bisect` | Временный линейный git-репозиторий из 1 024 коммитов, поломка начиная с 700-го | `git bisect run` находит коммит 700 за десять проверок |
| `nginx` | 30 потоков, общий barrier, пустая зона перед каждым режимом | 21 принятый запрос, девять 503; задержка до двух секунд без `nodelay`; с `return 200` все запросы обходят ограничитель |
| `postgres` | Таблица `orders`, один прогревочный запрос и три `EXPLAIN ANALYZE` на сценарий | Полные JSON-планы, медиана Execution Time, отдельно shared hit/read; уровень B-tree из pageinspect |
| `redis` | `PFADD` и `SADD` с одинаковым миллионом `user:N`, батчи по 1 000 | PFCOUNT, SCARD, MEMORY USAGE, политика вытеснения, размер выборки; дополнительно PFMERGE на пересекающихся множествах |
| `kernel` | Чтение `/proc/sys/net/netfilter/nf_conntrack_*` из контейнера | Только наблюдение, без изменения sysctl; часть параметров зависит от network namespace и может быть недоступна |

Кольцо показывает принцип consistent hashing. Это собственная учебная раскладка точек, а не побайтовая копия ketama в nginx. Числа нельзя использовать как тест совместимости с nginx.

У Postgres время включает выполнение плана, а не клиентский round trip через Docker CLI. Прогрев не гарантирует, что вся таблица поместится в shared buffers. `shared read` не равен физическому чтению устройства: данные может вернуть кеш ОС. Результаты не доказывают расход определённого числа ядер или скорость холодного диска.

У nginx запросы ранжируются по времени ответа, а не по номеру запуска потока. ОС и Docker вносят задержки, поэтому точное число принятых запросов около границы окна может меняться. Проверка допускает 20–23 ответа 200; конкретный сохранённый прогон показывает фактические числа. Скрипт проверяет, что ответов с неожиданными статусами нет и что `return` пропускает все 30 запросов.


## Сохранить репозиторий для git bisect

`make bisect` создаёт историю, находит первый плохой коммит и удаляет временный
репозиторий. Для самостоятельного разбора можно сохранить ту же историю:

```bash
# Из корня лабы; путь должен быть новым.
python3 scripts/lab.py bisect --repo /tmp/sre-bisect-demo
cd /tmp/sre-bisect-demo
git bisect start main main~1023
git bisect run sh ./check.sh
git bisect reset
wc -l < checks.log
```

Генератор создаёт 1 024 линейных коммита в ветке `main`. В каждом файл `version`
содержит порядковый номер коммита. Незакоммиченный `check.sh` проверяет, что номер
меньше 700: начиная с коммита 700 проверка завершается с ошибкой. На каждый запуск
он добавляет строку в `checks.log`; после одного поиска там десять строк.
Повторный поиск допишет ещё строки, поэтому счётчик относится ко всем запускам.

`--repo` только создаёт репозиторий: поиск запускаешь сам. Результаты в `results/`
при этом не перезаписываются. Существующий путь генератор отклоняет, включая
пустой каталог. Для ещё одного опыта выбери новый путь.
